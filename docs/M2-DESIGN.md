# M2 设计 — 断点续传 + Agent 技能

状态：方案待审 · 目标版本 v0.5.0
前置阅读：`docs/PROTOCOL.md`（SMQ1 帧格式与四层校验）

M2 只做两件事，做完即封版：

1. **断点续传** —— 接收端持久化接收进度、跨多次拍摄合并符号、GUI 图形化展示"已收/还缺"，
   并生成一个可带回发送端的**补播码**，让发送端第二次只播短缺部分。
2. **Agent 技能** —— 仓库内置一份 SKILL.md + 稳定的 CLI/JSON 契约，
   用户给 AI agent 一句提示词 + 仓库地址，agent 就能驱动发送播放与接收解码全流程。

---

## 1. 断点续传

### 1.1 关键判断（设计的立场）

**喷泉码下"断点续传"的本质不是重传指定符号，而是"跨场次累积符号 + 补足差额"。**

RaptorQ 的特性：接收端凑够**任意** K′ 个不同符号即可还原，不需要特定的源符号。
由此推出两个结论，整个 M2 围绕它们展开：

- **零协议改动就能续传**：发送端本来就是无限循环播放全部符号。接收端只要把
  已收符号集合持久化，第二次拍摄时加载上次的进度继续喂解码器，就已经是断点续传。
  这是 M2 的**主路径**，必须在 M2.1 就可用。
- **补播码只是时间优化**：告诉发送端"还差 N 个"，让它只播 N 个新的修复符号，
  把第二次拍摄从"完整一轮"缩到"差额 + 余量"。这是 M2.3 的增强，不阻塞主路径。

因此不引入"精确缺失符号清单"的复杂机制（接收端无法知道 RaptorQ 内部矩阵秩，
`raptorq` crate 的 Decoder 也不暴露），只用**唯一符号计数**估算差额，发送端补播时
加安全余量。简单、可证、够用。

### 1.2 接收端：进度清单 `.smr.json` + 载荷副本 `.smr.bin`

> **实现期修正（2026-09-22）**：初稿只持久化 ESI 集合，实现时发现此路不通——
> RaptorQ 解码器是增量构建的，续传必须用符号**载荷**重建解码器，仅知道
> "哪些 ESI 到过"无法续解。故检查点改为两个文件：JSON 存索引（合并键、
> 差额估算、录像列表），BIN 存符号载荷（与 `--dump` 相同的 u32 长度前缀帧序列），
> 续传时重喂 BIN 即精确回到上次停下的状态。BIN 体积 ≈ 已收数据量，
> 接收端在自由世界，磁盘不是约束。

每次解析（无论是否收满）都在录像旁落盘检查点：`<录像名>.smr.json` + `<录像名>.smr.bin`。

```json
{
  "format": "smr1",
  "session": "a1b2c3d4",
  "object_len": 52428800,
  "symbol_size": 1168,
  "blocks": [
    { "sbn": 0, "received": 31005,
      "ranges": [[0, 1204], [1209, 31004]] }
  ],
  "recordings": ["第一段.mov"],
  "updated_unix": 1758532800
}
```

- `session` = 容器 CRC-32（SMQ 帧里已有，hex 字符串）。
- `ranges` 为闭区间数组（接收大体连续，区间数远小于符号数；清单本身 < 1MB）。
- **合并键是 (session, object_len, symbol_size) 三元组**，不只是 session。
  现有协议里 session 只覆盖容器内容，同一文件换档位（T 不同）session 相同但符号流不兼容。
  合并时三元组不一致直接拒绝并提示"请用同一档位补拍"。这是本设计唯一踩到的协议坑，
  不动线上格式，用清单侧校验挡住。此外 `Receiver::push` 本身也加了同 session
  异 (F,T) 帧的丢弃守卫，双保险。
- 进度推进的核心改动在 `core::codec::Receiver`：`export_progress()` 导出索引；
  续传恢复不走"按索引重建"，而是把 `.smr.bin` 的帧重新 `push` 进新 Receiver——
  去重、OTI、解码器状态全部自然回来。core 不动帧格式、不动 RaptorQ 参数。

### 1.3 接收端：CLI 与 GUI

CLI（agent 主用，见 §2）：

```
sendmecongo-recv 第二段.mov --resume 第一段.smr.json --json 结果.json
```

- `--resume` 可重复多次（多段拍摄依次合并）。
- 收满 → 输出文件 + 四层校验照旧，清单标记完成。
- 未收满 → 退出码 `2`（部分接收），JSON 里带 `progress` 段与清单路径。

GUI 图形化（用户主用）：

- **每源块一个符号网格**：小方格 = 符号，已收实色、未收空色，悬停显示 ESI；
  块标签下显示 `已收 31005 / 需约 44912`。
- 总进度条 + 大字结论：**"还差约 13,907 个符号 ≈ turbo60 下 4 分钟"**
  （差额 ÷ 档位实测符号率，给拍摄时间预期，这是用户最关心的数）。
- 三个动作按钮：**保存进度**（默认自动）、**载入进度继续解析**、**生成补播码**。
- 网格数据直接来自 `Progress`，渲染成本 O(符号数)，64MB 上限约 5.5 万格，
  用 egui 的 painter 一次画完，无性能问题。

### 1.4 补播码（带回隔离机的反向通道）

隔离机没有输入通道，补播信息必须极小、可人工誊入。设计三档输入方式，按现场政策选用：

| 方式 | 内容 | 适用 |
|---|---|---|
| 手敲紧凑码（主路径） | base32，约 24 字符 | 严格隔离，只能键盘 |
| 导入 `.smr.json` | 整个清单 | 政策允许带入小文件 |
| 不用补播码 | 发送端照旧全量循环 | 差额大或嫌麻烦（主路径兜底） |

紧凑码格式（`SMR1` 负载，base32 无歧义字符集）：

```
magic(1B) | session(4B) | object_len(4B) | symbol_size(2B) | deficit(varint × Z) | crc8
```

单块文件（60MB 以下基本都是，见 §1.6）负载约 12B → **24 个字符**，分组显示：
`SMR1-XXXX-XXXX-XXXX-XXXX`。接收端 GUI 生成并大字展示；发送端 GUI 有"补播模式"
输入框，粘贴/誊入即可。

**差额估算**：`deficit = ceil((K′ − received_unique) × 1.05) + 8`。
K′ 取 K（源符号数）即可，RaptorQ 实际只需 K 加极小开销；1.05 余量 + 8 兜底，
宁可多播几秒。

### 1.5 发送端：补播模式

- 操作员选定**同一文件同一档位** → GUI 输入补播码 → 校验：
  本地重建容器，CRC-32 必须等于码内 session，(F, T) 必须一致，不符直接拒绝。
- 通过 → 只生成**新的修复符号**：ESI 从上次发射批之后接着编号
  （`Encoder::get_encoded_packets(repair_total)` 取更大 repair 数、跳过原批次），
  数量 = deficit，跨块轮转交织逻辑不变。
- 播放器照旧全屏循环，只是循环长度从"一整轮"变成"差额那一小段"。
- CLI 对应：`sendmecongo-send --file X --preset turbo60 --resume-code SMR1-... --play`。

**明确不做的**：不实现"按 ESI 精确补缺"。接收端给不出精确缺失集（矩阵秩不可见），
而喷泉码性质保证任意新符号都有用，精确补缺是伪需求。

### 1.6 边界与风险

- **多源块**：T≈1168 时单块上限约 56403 符号 ≈ 63MB，即绝大多数文件只有一块；
  64MB 上限边缘出现两块。网格与补播码都按 Z 块设计（varint 数组），
  但 UI 上单块时隐藏块概念，只显示一个网格。
- **换文件/换档位**：session 或 (F,T) 不符 → 拒绝合并、拒绝补播，文案明确。
- **清单损坏**：JSON 解析失败即忽略重来，不影响新拍摄（进度只是加速器）。
- **验收**：`docs/TESTING.md` 增加 L5 用例——拍 40% 停 → 解析存清单 → 补拍 40%
  → 合并收满；以及补播模式端到端（补播码誊入 → 短循环 → 收满）。跑分 JSON 照旧入 `out/`。

## 2. Agent 技能

### 2.1 形态

仓库内置 `skills/sendmecongo/SKILL.md`（YAML frontmatter + 操作手册），
用户把仓库地址给 agent，agent clone 后读 SKILL.md 即可上岗。
配套一份 `docs/AGENT.md` 定义机器契约（CLI  flags、JSON schema、退出码），
SKILL.md 引用它，二者同源不重复。

### 2.2 前置条件：CLI 面补齐

agent 不能点 GUI，现有程序要补三个脚本化入口（都是小改）：

| 程序 | 现状 | M2 补齐 |
|---|---|---|
| `sendmecongo-send` | 纯 GUI | `--file --preset --play [--size N] [--resume-code X]` 直启播放器；`--prepare-only --json` 干跑输出容器/符号统计 |
| `sendmecongo-recv` | 已有 CLI + `--json` | 加 `--resume`（§1.3）、退出码语义化（0 成功 / 2 部分 / 1 失败）、JSON 增加 `progress` 段 |
| `sendmecongo-bench` | 已脚本化 | 不动 |

JSON 输出契约（recv，节选）：

```json
{ "status": "partial", "received_file": null,
  "progress": { "session": "a1b2c3d4", "received": 31005, "needed_estimate": 13907,
                "manifest": "第一段.smr.json",
                "eta_seconds": { "turbo60": 232 } },
  "resume_code": "SMR1-XXXX-XXXX-XXXX-XXXX" }
```

`status: done` 时 `received_file` 为输出路径。agent 只认这一个 JSON，不解析 stdout。

### 2.3 SKILL.md 内容大纲

1. **何时用**：用户要从隔离环境取文件 / 给了本仓库地址。
2. **构建**：`cargo build --release`（技能里写明"播放必须 release"这条血泪教训）。
3. **发送流程**：问用户文件路径与档位（默认 turbo60 + 4K60 拍摄）→ `--prepare-only`
   汇报体积与预计拍摄时长 → 启动 `--play` → 把拍摄要领话术原样转达用户
   （固定手机、锁定 AE/AF、双通道档必须高帧率——从 docs/TESTING.md 摘成清单）。
4. **接收流程**：拿到录像路径 → `sendmecongo-recv 录像 --json` → 读 JSON：
   `done` 交文件；`partial` 把"还差多少、预计补拍多久、补播码"报给用户，
   并驱动 §1 的续传循环（存清单 → 用户补拍 → `--resume` 合并）。
5. **排障表**：符号率低 / 大面积 CRC 失败 / 双通道拍频——照抄 TESTING.md 翻车对照表。
6. **红线**：不替用户决定覆盖已有文件；>64MB 直接说明限制；不改动协议参数。

### 2.4 为什么不是 MCP server

评估过做成 MCP：发送端播放是长时间占屏的 GUI 进程、接收端是一次性批处理，
都没有常驻服务语义，CLI + JSON 契约已完全够用。SKILL.md 形态零依赖、
任何 agent（不只 WorkBuddy）都能用。M3 若做多文件批次守护进程再评估。

## 3. 里程碑拆分

| 里程碑 | 内容 | 复杂度 | 验收 |
|---|---|---|---|
| M2.1 | core `Progress` 导入导出 + recv `--resume` + 清单落盘 | 中 | 两段拍摄合并收满（CLI 层） |
| M2.2 | recv GUI 符号网格 + 进度/ETA + 补播码生成 | 中 | 人工目检 + L5 用例上半 |
| M2.3 | 补播码解析 + send 补播模式（GUI+CLI） | 中 | L5 端到端：补播短循环收满 |
| M2.4 | send/recv CLI 面补齐 + JSON 契约 + `docs/AGENT.md` | 低 | 契约示例全部可跑通 |
| M2.5 | `skills/sendmecongo/SKILL.md` + TESTING.md L5 + 实机验收 | 低 | agent 一句提示词走通全流程 |

依赖序：M2.1 → (M2.2 ∥ M2.4) → M2.3 → M2.5。
建议 M2.1 先单独合入发 v0.5.0-alpha，因为"跨拍摄合并"本身就已兑现断点续传的核心价值。

## 4. 明确排除（M2 不做）

- 加密封封（PROTOCOL.md 已列，独立成 M3 候选）
- 多文件批次与分卷
- 实时摄像头直收（仍是录像离线解析）
- 线上帧格式任何改动（M2 全程 SMQ v1 兼容）
